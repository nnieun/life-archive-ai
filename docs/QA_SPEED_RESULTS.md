# QA 응답 속도 개선 기록

측정일: 2026-10-05. Ollama 0.35.1, Windows, Ryzen AI 7 450 / Radeon 860M,
시스템 RAM 약 32GB. 측정 당시 Gemma는 CPU로 실행됐다.

## 측정 방법과 한계

개인 기억 대신 합성 기억 4개를 별도 SQLite에 만들고 같은 질문으로 비교했다.
실제 BM25/Chroma/외부 임베딩 호출 대신 고정 검색 결과를 사용한다. 따라서 아래 시간은
QA 그래프와 저장 시간이며, 실제 검색·서비스 최초 초기화·HTTP 왕복·화면 폴링 시간은 별도다.
실제 사용에서는 성공과 실패 모두 `qa_performance` 테이블에서 단계별 시간을 확인한다.
문답 내용은 성능 기록에 저장하지 않는다. 상세 실패 진단은 실패할 때만 저장한다.

초기 단계는 각 1회 측정이다. 누적 변경, 모델 로딩, 프롬프트 캐시와 시스템 부하가
함께 영향을 주므로 단계별 차이를 해당 변경만의 효과로 해석하지 않는다.
모든 성공 사례는 인용 ID와 기존 모델 검증, 원문 추적·숫자·인물 검사를 통과했다.
작은 합성 데이터 결과만으로 실제 기억 전체의 정확도를 보장하지 않는다.

## 적용한 동작

- 생성은 근거가 부족하면 빈 주장 목록을 반환한다. 서버가 근거 부족 응답으로 변환한다.
- 답변이 있으면 기존 의미 검증을 유지한다. 빠른 흐름에서는 원문·숫자·인물 검사를
  모델 검증 전에 실행해 명백한 오류에 추가 모델 호출을 쓰지 않는다.
- 입력 축소는 `sources`, `transcript_id`, 빈 필드를 프롬프트에서 제거한다.
  인용 좌표는 서버에 그대로 유지한다. 요약, 인물, 날짜와 불확실성 정보는 자르지 않는다.
  기존 생성 입력은 원문 전체를 보내지 않으므로 원문 길이의 임의 절단은 적용하지 않았다.
- 답변과 판단 이유를 짧게 요청하고 출력 상한을 설정한다. 잘린 출력은 통과시키지 않는다.
- 성공하며 인용이 있는 답변만 세션별로 캐시한다. 질문, top-k, 모델/임베딩/설정,
  프롬프트 버전, SQLite 기억·원문·인용 정보가 캐시 키에 반영된다.
  원문/기억/인용의 생성·수정·삭제 시 캐시를 비운다. 대화 삭제 시 관련 캐시도 삭제한다.
- 자동 재작성 기본값은 0회다. 검증 실패 시 빠르게 거절하며 잘못된 답변을 제공하지 않는다.
  답변 복구율이 중요한 상황은 `QA_MAX_REWRITES=1`로 기존 1회 재작성을 선택할 수 있다.
- 화면은 검색 → 작성 → 검증 상태와 경과 시간을 보여준다. 검색된 기억의 제목을 먼저
  확인할 수 있으며 다른 페이지에서도 작업과 완료 알림이 유지된다.
- 검증 전 답변 토큰 스트리밍은 적용하지 않았다. 검증된 답변만 제공하는 프로젝트
  규칙을 유지하며 진행 상태·검색 결과를 먼저 제공한다.

## 설정과 되돌리기

기본 프로필은 아래와 같다. 기존 `.env`에 항목이 없으면 새 기본값을 적용한다.

```dotenv
QA_COMBINED=true
QA_COMPACT=true
QA_CACHE_ENABLED=true
QA_NATIVE_OLLAMA=true
QA_VERIFICATION_MODEL=
QA_MAX_TOKENS=768
QA_MAX_REWRITES=0
OLLAMA_KEEP_ALIVE=15m
```

`QA_VERIFICATION_MODEL`이 비어 있으면 생성과 검증에 같은 모델을 쓴다.
별도 작은 검증 모델을 지정하면 모델 교체와 메모리 비용까지 함께 비교해야 한다.
기존 흐름은 `QA_COMBINED=false`, `QA_COMPACT=false`, `QA_CACHE_ENABLED=false`,
`QA_NATIVE_OLLAMA=false`, `QA_MAX_REWRITES=1`로 선택할 수 있다.
설정 변경 후 백엔드를 재시작한다. 프론트엔드도 재시작해 새 응답 필드를 읽게 한다.

모델을 15분 유지하면 메모리를 계속 사용한다. 필요하면 `ollama stop gemma4:e2b`로 해제한다.
Gemma 기본값과 OpenAI 임베딩 모델은 이번 작업에서 변경하지 않았다.

## 재현 및 운영 기록 확인

```powershell
.\.venv-review\Scripts\python.exe scripts/benchmark_qa.py --label repeat_fast --combined --compact --native --max-tokens 768 --max-rewrites 0 --repeat 3
.\.venv-review\Scripts\python.exe scripts/benchmark_qa.py --label repeat_cache --combined --compact --native --max-tokens 768 --max-rewrites 0 --cache --repeat 2
.\.venv-review\Scripts\python.exe scripts/inspect_qa_performance.py --limit 20
```

`--model`로 생성 모델, `--verification-model`로 검증 모델을 바꿔 비교한다.
평가 스크립트는 로컬 Ollama만 사용하며 LangSmith 추적을 끈다.
운영 성능 기록에는 질문·답변·기억 본문·제목·API 키를 저장하지 않는다.

## 비교 범위

GPU 가속, 장비 교체와 유료 외부 서버는 이번 로컬 코드 개선과 별도다.
새 서버나 장비를 확보하지 않았으며 기존 GPU 설정도 변경하지 않았다.
추가로 `qwen3:1.7b`를 다운로드해 단독 모델과 생성/검증 모델 분리를 비교했다.
현재 단순 질문에서는 Gemma 단독보다 뚜렷한 속도 이득이 없어 기본 모델과
검증 모델을 Gemma로 유지한다. Qwen3 모델 파일은 로컬에 남아 후속 비교에 사용할 수 있다.
더 많은 실제 질문으로 정확도를 비교하기 전까지 작은 모델이 동등하다고 판단하지 않는다.

프로필별 중앙값이나 단일 차이만으로 일반적인 속도 향상률을 주장하지 않는다.
긴 질문·처음 보는 근거·콜드 로딩은 위의 반복 질문보다 오래 걸릴 수 있다.

Native API의 `format`, `think`, `keep_alive`와 처리 시간 항목은
[Ollama 공식 Chat API](https://docs.ollama.com/api/chat)를 기준으로 적용했다.

## 후속 수정: 인물 질문의 과도한 근거 부족 판단

통합 프롬프트에서 인물 식별 지침이 부족해, 인물이 실제로 검색된 기억에 있어도
모델이 직접적인 인물 소개가 없다는 이유로 답변을 거절한 사례를 확인했다.
인물 질문에는 기록된 역할·행동으로 답할 수 있고, 사건 날짜의 불확실성은
인물과 행동의 근거까지 없애지 않는다는 지침을 추가했다. 호칭만으로 가족관계를
만들지는 않으며 최종 검증도 유지한다.

운영 DB의 같은 질문·검색 결과로 읽기 전용 재현을 수행했고 답변 생성과 검증이
11.61초에 통과했다. 이 재현은 문답이나 원문을 평가 파일에 복사하지 않았다.
관련 자동 테스트 43개도 통과했다. 프롬프트 버전이 캐시 키에 반영되어 이전
프롬프트의 캐시를 재사용하지 않는다.

합성 후속 실험 20: 기억에 없는 생일 질문은 5.480초에 여전히 근거 부족으로 거절했다.
후속 실험 21: 호칭과 불확실한 사건 날짜가 함께 있는 인물 질문은 8.694초에
답변과 검증을 통과했고 두 연도의 불확실성을 유지했다.
